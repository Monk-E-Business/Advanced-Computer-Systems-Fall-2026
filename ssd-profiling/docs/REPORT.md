## 2. Pre-experiment hypotheses

*Written before any measurement. Commit this section (git timestamp) before
running `make all`, and do not edit it afterwards — §9 compares against it.*

**H1 — QD=1 latency.** 4 KiB random **read** ≈ 50–100 µs: dominated by the NAND
array read (tR ≈ 40–80 µs for TLC) plus ~10 µs of controller, PCIe and host
stack. 4 KiB random **write** at QD1 will be *lower* than read (≈ 10–30 µs)
because the drive acknowledges once data is in its DRAM/SLC write buffer; the
NAND program (hundreds of µs) happens later. 128 KiB sequential read ≈ 100–200 µs
(NAND read across several dies + ~20–40 µs of transfer at link speed;
controller read-ahead may help); 128 KiB sequential write ≈ 40–100 µs (buffered).
p99 ≈ 1.5–3× the mean for reads; writes have a heavier p99.9 from buffer flushes/GC.

**H2 — Block size.** Throughput rises with block size because per-command
overhead is amortised, until it hits the NAND parallelism or the link ceiling
(≈ 64–128 KiB for sequential). IOPS falls with block size. Latency is nearly
flat for small blocks and grows ~linearly once transfer time dominates. On NVMe,
random ≈ sequential at ≥ 64–128 KiB because a large random I/O is striped across
many dies anyway.

**H3 — Read/write mix.** Total IOPS for mixes will be *below* the linear
interpolation between 100% read and 100% write: reads block behind NAND programs
and erases on the same die. Read mean and especially read p99 rise as the write
fraction rises.

**H4 — Queue depth.** IOPS grows almost linearly with QD while the device's
internal parallelism (channels × dies × planes) has idle units; latency stays
near the QD1 value. Past the knee (expected QD ≈ 16–64 for 4 KiB random read)
throughput plateaus and, by Little's Law (W = L / X with X flat), mean latency
grows proportionally with QD. A single submitting thread may become CPU-bound
(≈ 150–400 k IOPS through `windowsaio`/IOCP, depending on the CPU) before a fast
drive saturates; the multi-job series should reach a higher plateau.

**H5 — Tail latency.** The p99/p50 and p99.9/p50 ratios grow toward the knee
(queueing turns service-time variance into waiting-time variance, cf. M/M/1
waiting time ∝ 1/(1−ρ)). A 70:30 mix at the knee adds a millisecond-scale read
tail caused by program/erase interference.

**H6 — Working set.** With on-board DRAM holding the full mapping table, 4 KiB
random read is flat across LBA spans. A DRAM-less (HMB) drive will be faster on
small spans and slower on large spans (mapping-table misses add an extra NAND
read at QD1).

**H7 — Device state.** Random-write IOPS starts high (burst, free blocks
available) and decays to a steady state ≈ 20–50% of burst once garbage collection
must run (write amplification). Sustained sequential write drops sharply
(the "SLC cliff") after tens–hundreds of GB, depending on capacity and free space.
Thermal throttling only if the composite temperature reaches ≈ 70–80 °C.

**H8 — Misleading setups.** Buffered random reads on a RAM-resident working set
will report several hundred k IOPS at a few µs (Windows file cache), with
near-zero bytes in the volume's I/O counters. A synchronous engine with
`iodepth=32` will behave exactly like QD1 (Little's L ≈ 1), and `iodepth=32` ×
4 jobs will put ~128 I/Os in flight, not 32. Reads of an extended-but-never-written
file return zeros without device reads, so they report impossibly high IOPS.

**H9 — NTFS valid data length (Windows).** Random 4 KiB writes into a file whose
end-of-file was set without writing data will make NTFS zero-fill from the
valid data length up to each write offset first. The volume should see many
times more bytes written than fio issued, with individual writes taking
milliseconds to hundreds of milliseconds.

## 10. Threats to validity

*NTFS file vs raw disk (filesystem metadata I/O, cluster size); same physical
SSD as Windows (OS background I/O on C: still reaches the drive, even though the
volume counters exclude it); Defender, indexing, Update and other background
activity; span < full capacity (more free space ⇒ better steady state than a
full drive); partial preconditioning; single drive, single host; Windows can't
isolate CPUs the way Linux `isolcpus` can, so pinning only restricts fio;
temperature not controlled; power-plan and CPU frequency effects on host-side latency.*
